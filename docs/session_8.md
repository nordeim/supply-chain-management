Since runs #6 and #7 executed bit-identical app code, this was a flake or environment change, not a regression — and the job's total duration (1m41s, shorter than the green run #5's 1m53s) proved the 5s `expect` timeout failed fast rather than burning the webkit project's 60s per-test budget.

Root cause: a hydration race. Playwright **actions don't retry** (assertions do). The products search test fills an SSR-rendered searchbox and presses Enter directly — on a slow shared runner those actions can land before the products page's client island hydrates, so the submit is unwired (or falls through to the browser's implicit GET with no input name), and the URL never gains `?q=`. Runs #5/#6 passed on faster runners; run #7 lost the race. Auth specs are immune because opening the sign-in dialog itself proves hydration; the procurement filter test's option-locator wait acts the same way.

Remediation, validated red/green locally before delivery:
W1 (two layers) — (a) the spec wraps interact→assert in `expect(async () => { fill; press; toHaveURL(2s) }).toPass({ timeout: 20s })`, Playwright's canonical remedy for action-level races; (b) the search inputs in `products-filters.tsx` and `order-filters.tsx` carry `name="q"`, so a pre-hydration Enter triggers the browser's implicit GET submission with the correct query and the server renders the filtered table — post-hydration the attribute is inert (handleSubmit preventDefaults; the URL flow stays router-driven). A deterministic local simulation (JS-bundle route delay + `waitUntil: 'domcontentloaded'` + stripping `name="q"` from the SSR HTML to emulate the pre-fix component) reproduced the run-#7 failure with the old pattern (RED), proved the toPass retry rescues even the old component (GREEN), and proved the `name="q"` implicit-GET path works standalone. All three interleavings are now deterministic; the full chromium suite re-ran 31/31 after the throwaway simulation spec was deleted.
